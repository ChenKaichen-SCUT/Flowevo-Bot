# Flowevo-Bot V4：自动组合式数学宏策略发现与泛化验证

## 一、总体任务

请继续在 GitHub 仓库 `https://github.com/ChenKaichen-SCUT/Flowevo-Bot` 中推进研究，以提交 `ebe50279392e8a6d0ad717ef0cd33922115552ca` 为本轮参考起点。

你是一名负责 LLM Agent、程序合成、数学符号计算、自动验证与科研实验的高级研究工程师。

本次要求实际完成代码审计、算法改进、离线实验和必要的条件式验证，并生成可供下一轮科研分析的完整报告与数据。不要只提出设计方案。

### 已有结果

上一轮 Flowevo-Bot V3 使用 603 条干净训练首次成功轨迹，自动合成了两条经过数学验证的标量程序：

- 根和：基于多项式首项系数与次高次项系数；
- 根积：基于常数项、首项系数及次数奇偶性。

目标文法、基础数学算子、DSL 和验证规则仍由人工设计。

在原开发集 1,549 题上的完整任务执行情况：

| 方法 | 完整执行 | 仅局部可用 | 其他回退 |
|---|---:|---:|---:|
| 人工数学工具 B | 20 | 12 | 1,517 |
| 自动合成宏库 C | 2 | 12 | 1,535 |

在此前独立保留的 1,115 道题中，仅有 1 道可完整执行。

本轮没有达到付费实验门槛，没有新增 DeepSeek API 调用，也没有运行 MATH-500。

### 核心判断

当前问题不再主要是已有计算公式的正确性，而是：

1. 603 条成功轨迹中，能够被当前系统识别成可学习数学操作的轨迹太少。
2. 当前 DSL 只能合成标量系数表达式，难以表达多步骤数学变换。
3. 自动宏仍然没有覆盖人工数学工具无法处理的新任务。
4. 目标类型及数学语义解析范围有限，导致完整任务覆盖率很低。
5. 自动宏的来源结构与独立验证题数量不足，无法支持泛化和 token 摊销的主张。

**本轮研究问题：能否从不同数学题的成功轨迹中，自动发现、组合并验证中等粒度的数学变换流程，使自动 Skill Bank 能处理原本需要完整调用 LLM 的新任务？**

特别注意，本轮不以人工添加更多公式作为主要研究贡献，也不能将人工预写的 SymPy 操作重新命名为自动学习的 Skill。

## 三、Stage 1：分析为什么 603 条轨迹只产生 9 条可学习操作

这是本轮的第一优先级。

```text
603条干净成功轨迹
    ↓
能够解析题目目标
    ↓
能够提取数学对象
    ↓
能够识别数学变换步骤
    ↓
能够抽取输入/输出关系
    ↓
能够归入重复数学结构
    ↓
具备足够独立来源
    ↓
DSL可以表达
    ↓

    ↓
```

每一步都必须记录真实数量和拒绝原因，不允许只报告最终产生两条宏。

**问题 A：轨迹没有复用价值。**

**问题 C：聚类或来源数量不足。**

**问题 E：验证器表达能力不足。**

## 四、Stage 2：从真实轨迹中发现可复用的多步骤数学结构

本轮不再只学习如下单一系数公式：

```text
root_sum = -a[n-1] / a[n]
```

而是尝试学习能够由多个数学操作组成的宏策略。

重点研究以下形式：

```text
识别数学对象
    ↓
规范化或变换表达式
    ↓
应用一种数学关系
    ↓
得到简化结构
    ↓
执行下一步变换或计算
    ↓
验证结果
```

### 4.1 先依据数据选择候选方向

允许探索：

- 多项式规范化、除法与余式；
- 因式分解与可逆代换；
- 有理表达式降阶；
- 对称表达式和多项式关系；
- 数论中的整除、同余与有限候选筛选；
- 简单递推关系和结构化计数。

但不能因为这些方向看起来有用就全部实现。

**优先选择训练轨迹中确实反复出现、具有明确输入输出关系和独立来源的数学结构。**

不要求七个 MATH 学科全部产生新宏。

### 4.2 改进 ReasoningOperation

建议将记录扩展为：

```text
ReasoningOperation:
    operation_type
    input_type
    output_type
    input_structure
    output_structure
    preconditions
    transformation
    source_task_id
    source_step_ids
    verification_rule
    extraction_confidence
    provenance
```

需要区分：

- 自动识别出的数学操作；
- 从解题文本中直接复制的内容；
- 由人工文法提供的数学语义；
- 已经得到符号验证的操作；
- 未能可靠解释的自然语言步骤。

不能把提取到某段 LaTeX 等式视为成功理解完整推理链。

### 4.3 跨题结构归纳

研究通过变量重命名、表达式规范化、结构匹配和受限反统一（anti-unification），识别不同数学题之间共有的变换流程。

例如，两道题表述不同，但均包含：

```text
原始多项式
→ 规范化
→ 转化成可计算的代数对象
→ 执行同一种关系
→ 恢复目标量
```

若输入结构和数学条件可参数化，可以形成候选宏。

必须保留每条宏的来源题及变换步骤。

不要把只在一道题中出现的特殊解法强行提升为通用算法。

## 五、Stage 3：设计可组合的类型化 DSL

当前 V3 DSL 主要使用：

- 系数特征；
- 奇偶特征；
- 加、减、乘、除；
- 有界 AST 搜索。

本轮在确认数据需要后，尝试扩展成**类型化数学变换 DSL**。

### 5.1 类型系统

至少考虑以下类型：

```text
Scalar
Polynomial
RationalExpression
Equation
ConstraintSet
FiniteCandidateSet
```

如果某个类型没有真实数据支持，可以暂缓实现。

### 5.2 基础操作

可以根据来源轨迹引入受限操作，例如：

- 多项式规范化；
- 有理式约分与定义域维护；
- 多项式商和余式；
- 系数提取；
- 多项式代换；
- 因式分解；
- 合法的等价变形；
- 简单整除和模运算约束；
- 候选集过滤。

这些基础操作属于**人工提供的 DSL 原语**，而不是自动学习的成果。

自动学习应体现在：

> 系统从成功轨迹中自动发现哪些原语应该按什么顺序组合、在什么前置条件下执行、如何得到目标结果。

必须记录人工先验与自动学习部分，避免混淆。

### 5.3 程序搜索

实现有界、类型安全的组合程序搜索。

优先考虑：

- 类型约束；
- AST 规范化；
- 重复子表达式去重；
- 搜索深度与节点数上限；
- 中间值的精确类型；
- 输入输出样本约束；
- 数学 Guard；
- 反例驱动排除错误程序。

如果使用已知数学计算库，必须明确区分：

- 使用通用基础算子；
- 人工预写完整解法；
- 自动搜索得到的复合程序。

不能把调用人工预写余式求解器这一动作本身视为自动发现余式宏。

### 5.4 数学验证

候选程序应尽量使用独立数学性质进行验证，例如：

- 表达式等价；
- 多项式恒等式；
- 除法算法的商余关系；
- 代换的定义域和可逆性；
- 同余条件；
- 方程或约束集合保持。

验证必须与训练样本拟合分开。

对于存在不等价变形、信息丢失或无法证明前置条件的程序，应拒绝直接执行。

不能运行未经限制的 LLM 生成代码；只能执行受信任 DSL 中的操作，并设置复杂度、运行时间和内存上限。

### 6.1 验证什么？

对于每条新宏，除了数学正确性，还需要验证：

1. 能否匹配来源题之外的新题？
2. 是否覆盖不同的表面表达？
3. 是否覆盖不同的数学结构变体？
4. 是否只记住训练中的特定数值？
5. 是否依赖人工预置的完整解法？
6. 是否能够真正完成新题，而非只给出中间量？

候选必须由不同来源支持，不能通过简单修改数字或变量名制造验证数量。

## 七、Stage 5：严格比较人工工具与自动宏的新增价值

本轮必须继续保留三个对照：

### A：Bot-NoBank

直接使用 DeepSeek Flash。

### B：Manual Mathematical Tools

使用固定 Goal Parser、人工预置数学工具、Guard 和独立验证器。

### C：Automatically Synthesized Macro Bank

使用相同 Goal Parser、可访问的基础原语和验证机制，但真正执行从训练轨迹中自动合成并通过验证的程序。

**B 与 C 的主要差别应是数学操作组合是否由系统自动发现，而不是给 C 更强的人工先验。**

至少报告：

| 指标 | B 人工工具 | C 自动宏 |
|---|---:|---:|
| 完整可解析目标数 | 实测 | 实测 |
| Guard 通过数 | 实测 | 实测 |
| 完整执行数 | 实测 | 实测 |
| 独立验证正确数 | 实测 | 实测 |
| C 相对 B 新增覆盖 | — | 实测 |
| 需要 LLM 回退数 | 实测 | 实测 |
| 数学工具运行成本 | 实测 | 实测 |

尤其要统计：

- B 和 C 都可以解决的题；
- 只有 B 能解决的题；
- 只有 C 能解决的题；
- 两者都不能解决的题。

如果 C 只是复制了 B 已有的公式，虽然自动搜索本身正确，也不能宣称获得了额外推理能力或 token 收益。

如果 C 覆盖率相同，但确实降低了人工建库成本，也可以作为独立的工程发现记录，但不能将其冒充推理 token 节省。

### 8.1 付费实验启动门槛

在访问新的独立确认题之前，预先冻结启动条件。

建议至少要求：

1. 有真正自动合成且经过验证的复合宏，而不只是标量已知公式。
2. 在独立开发数据中有足够数量的 eligible 题。
3. 覆盖至少数种实质不同的数学结构。
4. 自动宏相对于人工工具出现新的完整任务覆盖，或有明确可检验的额外成本优势。
5. 数学正确性和语义 Guard 测试全部通过。
6. 没有出现不可接受的错误接管。

如新独立数据仍然稀缺，不得反复调整门槛凑出可运行样本。

### 8.2 实验规模

如果门槛满足，可以开展一次最小规模的独立开发验证。

建议：

- 约 12～30 道符合条件的独立题；
- 包含少量不符合 Trigger 的对照题；
- A/B/C 三组配对；
- 最多 120 次新增真实 API 调用；
- 最多 200,000 新增 tokens。

这些是预算上限，不是必须耗尽。

超出预算前停止并报告。

如果门槛不满足，直接结束本轮，不得为了得到模型实验结果而强行扩大范围。

### 8.3 评测指标

除正确率、输入/输出 token 外，必须记录：

- 真实跳过 LLM 的任务数；
- 自动宏完整求解数；
- 因语义解析失败而回退的任务数；
- 因数学 Guard 失败而回退的任务数；
- 因 DSL 不支持而回退的任务数；
- 因验证失败而回退的任务数；
- 每个自动宏的来源题和独立使用次数；
- 自动合成及验证成本；
- B/C 相对于 A 的 token 节省；
- C 相对于 B 的额外收益。

不得将离线推测能够省掉的 tokens 报成真实测得的 API 节省。

## 九、Stage 7：机制归因与研究决策

最终必须回答：

**RQ1：自动程序学习是否成功？**

系统是否真正从成功轨迹中自动发现了多步骤、可复用的数学操作，而不是检索人工预写公式？

**RQ2：是否实现跨题泛化？**

这些程序能否解决来源题之外、数学结构存在真实差异的新题？

**RQ3：自动学习是否优于人工工具？**

相同基础原语和 Goal Parser 下，自动 Macro Bank 是否提高完整任务覆盖率、降低成本，或减少必要的人工工作？

**RQ4：是否有可能在整个 MATH 分布上摊销？**

不仅看 eligible 子集上的节省，也要结合整体覆盖率、建库费用以及需要回退的比例。

**RQ5：继续研究是否值得？**

如果扩大 DSL 后仍然只能生成少量已知标量公式，或者没有足够独立验证题，应考虑停止自动可执行宏路线的规模化 token 收益主张。

不能无限追加人工算子来维持研究进展。
