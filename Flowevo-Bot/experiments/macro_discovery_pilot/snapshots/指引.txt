# Flowevo-Bot 下一阶段研究指引：高价值数学宏策略发现与计算复用可行性验证

## 一、研究背景与核心目标

你是一名负责 LLM Agent、数学推理、程序分析、Skill Learning 和实验复现的高级研究工程师。

当前已有三个代码项目：

- FlowEvo
- Buffer of Thoughts（BoT）
- Flowevo-Bot

后续所有研究继续在已有的 Flowevo-Bot GitHub 仓库中推进：

https://github.com/ChenKaichen-SCUT/Flowevo-Bot

上一轮代码版本为提交 `206a6caa6954283e41f219d6c61f84f6904eb5f8`。开始前必须核对实际本地版本、远端版本和未提交修改，不要假设当前工作树完全等于该提交。

### 1.1 已有实验结论

上一轮在 20 道独立开发题上的三组对照结果如下：

| 方法 | 正确率 | 输入 tokens | 输出 tokens | 总 tokens |
|---|---:|---:|---:|---:|
| Bot-NoBank | 18/20 | 2,252 | 23,476 | 25,728 |
| 原 Skill | 19/20 | 3,432 | 23,004 | 26,436 |
| V2 Skill | 19/20 | 3,862 | 24,717 | 28,579 |

本轮 V2 已实现：

- 数学评分器改进；
- 结构化 Trigger/Guard；
- 多轨迹 Thought Distillation；
- Shadow Admission；
- Skill 来源追踪；
- 完整 token 账本；
- 防 gold-answer feedback 测试。

但是结果说明：

1. 两条 V2 Skill 仍未成为 active。
2. 实际注入后的总 token 反而增加约 11.1%。
3. 唯一新增成功主要来自 NoBank 的输出截断，而不是已验证的数学能力改善。
4. 当前 S04、S07 的覆盖率和成本表现不足以证明它们具有稳定复用价值。
5. 将更多通用解题建议注入 prompt，可能增加模型输入和输出长度。

因此，本轮不应继续简单扩充原有策略库。

### 1.2 本轮核心研究问题

**能否从已有真实数学解题轨迹中，发现重复出现且值得复用的中等粒度数学推理结构，将其提炼成能够替代部分 LLM 推理的宏策略，并在独立题目上保持正确率、减少总 token？**

特别区分：

- 题目内容相似；
- 使用同一种解题套路；
- Skill 被检索或注入；
- Skill 真正替代了部分推理；
- Skill 产生了端到端 token 净节省。

这五件事不能混为一谈。

本轮的优先目标是证明“某些数学推理结构确实值得复用”，而不是提升整体 Skill 注入率。

# 四、Stage 2：挖掘重复出现的数学推理结构

这是本轮最重要的研究步骤。

过去 Distiller 的主要问题是依赖解题文本关键词和题目表面特征，因此可能把数学方法不同的题聚在一起，或者把使用相同数学方法的题错误分开。

这次需要重点识别：

**模型在解题时实际进行了什么数学变换。**

## 4.1 建立数学推理结构分类

先根据 MATH 的七类学科对轨迹分类：

- Prealgebra
- Algebra
- Intermediate Algebra
- Geometry
- Number Theory
- Counting & Probability
- Precalculus

然后在学科内部识别常见的推理结构。

候选包括但不限于：

**代数**

- 分组因式分解；
- 对称表达式化简；
- 有理式代换降阶；
- 方程等价变形；
- 根与系数关系；
- 将复杂表达式化为可求解的标准形式。

**数论**

- 素因子结构约束；
- 模运算排除不可能情况；
- 整除与最大公因数关系；
- 特殊素数的分类讨论；
- 数论约束转有限候选枚举。

**计数与概率**

- 互斥分类计数；
- 补集计数；
- 容斥；
- 组合结构分解；
- 对称性及重复计数消除。

**几何**

- 相似三角形关系；
- 面积关系转换；
- 坐标化；
- 勾股关系与长度约束；
- 辅助变量引入。

**预微积分**

- 三角恒等式化简；
- 数列与递推结构；
- 函数变换；
- 周期性与范围限制。

以上是候选方向，不代表已经存在值得入库的 Skill。

最终应根据真实轨迹证据选择，而不是为了覆盖全部学科而强行生成。

## 4.2 不能只用关键词聚类

例如两条轨迹都包含 `factor`，不代表它们使用相同的数学策略。

尽可能识别数学操作的输入结构、变换和结果：

```text
原始表达式结构
    ↓
执行的数学变换
    ↓
产生的简化结构
    ↓
该变换的数学前置条件
```

建议研究和实现：

- LaTeX 表达式解析与规范化；
- SymPy 可识别的代数表达式结构；
- 常见变换模式检测；
- 解题步骤的类型化表示；
- 可验证的符号等价关系；
- 对同构数学结构进行变量重命名和规范化；
- 对不能形式化解析的证明型推理保留人工或 LLM 辅助审查接口。

不能假装所有自然语言数学推导都能被 SymPy 自动证明。

对于无法可靠识别的步骤，应标记为 `unparsed` 或 `unknown`。

## 4.3 构建数学推理结构中间表示

建议设计：

```text
ReasoningOperation:
    operation_type
    input_structure
    output_structure
    assumptions
    required_guards
    source_step_ids
    verification_status
```

再将多个操作聚合成中等粒度的宏结构。

例如：

```text
识别有理式结构
    ↓
引入合法代换
    ↓
降为低阶方程
    ↓
求解简化问题
    ↓
恢复原变量及定义域检查
```

该结构才有可能成为可复用的宏策略。

## 4.4 统计真实频率

对每一种发现的数学宏结构，至少统计：

- 涉及多少道不同题；
- 出现在哪些学科；
- 来源题的结构差异；
- 每道题中该结构承担什么作用；
- 是否存在相同输入结构但不同解法；
- 是否存在明显不适用的反例；
- 是否能执行或自动验证部分步骤。

不要只统计出现次数，还要判断它是否真正提供了足够多的可替代推理步骤。

## 4.5 输出

生成：

- `02_REASONING_PATTERN_MINING.md`
- `data/reasoning_operations.jsonl`
- `data/pattern_clusters.json`
- `data/pattern_frequency.csv`
- `data/pattern_examples.md`

报告中必须展示至少若干个真实题目及其共同数学变换，不得用编造示例代替实验数据。

# 五、Stage 3：筛选具有实际计算价值的宏策略

不要对全部发现的 pattern 立即调用 LLM 生成 Skill。

先进行价值筛选。

## 5.1 候选 Skill 的三个主要维度

**Coverage**

该宏结构是否在足够多的不同数学题中出现？

**Substitution Potential**

是否能够替代原本需要 LLM 重新生成的一段真实推理或计算？

**Reliability**

适用条件能否判断，数学变换是否能可靠执行或检查？

## 5.2 筛选原则

不优先选择：

- 仅出现一次的特定技巧；
- 只适用于改变数字的模板；
- 内容非常笼统的策略建议；
- 难以识别适用条件的复杂套路；
- 需要注入大量文字才能指导模型的 Skill；
- 预计只能节省少量 token，却需要高额构建成本的 Skill。

优先选择：

- 在多道不同题中重复出现；
- 具有明确的触发结构；
- 包含较完整的数学推理子流程；
- 可由简短模板表达；
- 部分计算可被符号程序执行；
- 可以验证数学前置条件；
- 有合理的未来复用机会。

## 5.3 估计潜在净收益

基于独立开发数据中的历史轨迹，估计候选宏策略的可能覆盖率。

估算：

```text
expected_eligible_rate
expected_prompt_overhead
estimated_replaceable_reasoning
expected_verification_cost
estimated_build_cost
expected_break_even_uses
```

这些估计必须标明证据与不确定性。

不能仅凭“某个解答步骤看起来很长”，就认定使用 Skill 一定能够减少同等数量的输出 token。

真实的 token 收益仍必须通过后续模型实验测量。

## 5.4 最终候选

本轮只选择 **2～3 个最有潜力的数学宏策略家族**。

不要求固定包含 S04、S07。

如果历史数据表明另外的策略具有更好的覆盖率与计算替代潜力，应优先考虑新的策略。

如果所有候选都缺乏合理价值，应报告结果并停止，不要强行生成 3 个。

## 5.5 输出

生成：

- `03_MACRO_CANDIDATE_RANKING.md`
- `data/macro_candidates.json`
- `data/macro_screening.csv`

对每个候选明确说明为什么选它、为什么没选择其他候选，以及当前尚未得到验证的假设。

# 六、Stage 4：实现两种不同的 Skill 复用方式

对于筛选出的 2～3 个候选宏策略，分别研究：

### Route A：Compact Thought Skill

借鉴 BoT，将数学宏策略压缩成简短的解题指导。

每条 Skill 应包含：

- 适用结构；
- 主要解题步骤；
- 关键数学 Guard；
- 常见错误；
- 简短注入文本。

建议初始 prompt 长度上限为约 100 tokens，可配置。

注意：这是短提示路线，并不保证节省 token。

### Route B：Executable Macro Skill

尝试将宏策略中可以确定性完成的部分实现为数学程序。

例如：

- 可验证的代数化简；
- 明确条件下的因式分解；
- 简单同余约束；
- 符号方程变换；
- 标准组合计算；
- 明确的变量代换和回代。

优先借助已有数学工具，而不是让 LLM 每次重新输出完整计算。

但必须严格区分：

**完整任务的可靠解答**与**只完成某个中间数学步骤**。

中间步骤得到验证，不代表整个数学题已经解决。

只有能够独立验证最终结果时，才允许不调用 LLM 直接提交。

否则应将得到的可靠中间结果作为短上下文，再由 LLM 完成剩余推理。

如果某个宏策略根本无法安全编译为可执行程序，应保留为 Prompt Skill，不要伪造可执行实现。

## 6.1 Trigger 和 Guard

继续使用 V2 的结构化 Trigger/Guard。

Trigger 只根据当前题面和可观察数学结构判断。

Guard 检查使用某个数学变换的合法性。

不能读取当前测试题 gold answer 进行 Trigger、Guard 或 fallback 决策。

## 6.2 两种 Skill 的主要区别

Compact Thought Skill：

```text
识别套路
→ 注入短策略
→ LLM 解决题目
```

Executable Macro Skill：

```text
识别套路
→ 检查数学 Guard
→ 执行可验证的数学计算
→ 必要时让 LLM 完成剩余推理
```

最终必须比较这两种路线是否真正节省 token。

不能预先认定可执行路线一定更好，因为检索、解析、验证以及解释计算结果也可能增加开销。

## 6.3 输出

- `04_MACRO_IMPLEMENTATION.md`
- `data/macro_skill_bank.json`
- 可执行数学宏策略源码
- 数学正确性与 Guard 测试
- 每个宏策略的适用与拒绝案例

# 七、Stage 5：离线检验与进入实验的门槛

在任何真实模型调用前，先执行离线测试。

至少验证：

1. Skill 能否匹配其合理的来源题。
2. 是否会错误匹配明显不适用的题。
3. Trigger 的 AND/OR 逻辑是否正确。
4. 数学 Guard 是否处理边界条件。
5. 变量代换是否恢复原始定义域。
6. 是否存在因清分母产生的增根。
7. 符号计算步骤是否能够可靠验证。
8. 是否能区分局部验证和整题成功。
9. 是否存在 gold-answer 泄漏。
10. Token 记录接口是否完整。

对于可执行算子，添加性质测试和明确的反例测试。

如果无法证明其普遍正确性，应限定到已经验证的适用范围，不能把随机抽样通过当成形式化正确性证明。

若候选不能通过基本数学正确性和适用性测试，应当停止该候选后续实验。

只有至少一个候选通过离线测试，才进入真实 API 小实验。

# 八、Stage 6：小规模真实 DeepSeek Flash 实验

本阶段验证：

**是否真的存在能够比 Bot-NoBank 节省 tokens 的数学宏策略。**

本轮暂不运行完整 MATH-500。

## 8.1 模型与并发

沿用此前配置：

- 模型：DeepSeek Flash
- API 最大并发：64
- 本地计算最大并行：12

这两个数是上限。小规模实验应按实际负载选择合理并发，不需要为了用满 64 而人为增加任务。

要求：

- 记录完整 token usage；
- 保存请求与响应；
- 可以断点恢复；
- 区分基础设施重试与解题重试；
- 不发生 gold-answer feedback；
- 不允许根据测试正确性动态重试；
- 不得在同一个正式评估过程中修改已冻结 Skill。

## 8.2 测试题选择

对于每个进入实验的 Skill 家族，从独立开发数据中选择约 10～12 道真正符合适用结构的题。

尽量保证：

- 不与 Skill 来源题重合；
- 不是简单替换数字；
- 具有一定题面和结构差异；
- 包含不同难度；
- 有可靠的离线评分方式。

如果某个候选的独立 eligible 题不足，不要放宽数学条件凑数。

同时保留 eligible 题的总体筛选分母，以便报告覆盖率，不能只在精心挑选的匹配题上展示成功率。

## 8.3 三组核心对照

**A：Bot-NoBank**

直接使用 DeepSeek Flash 解题。

不注入任何 Skill。

**B：Bot + Compact Thought Skill**

注入简短的数学解题宏策略。

**C：Bot + Executable Macro Skill**

尝试执行可验证的数学宏操作，必要时调用 DeepSeek Flash 完成剩余部分。

对于不支持执行的宏策略，明确标记 C 不适用，不得偷偷等同于 B 后再报告成独立方法。

三组应使用相同的基础 prompt、答案格式和模型生成预算。

如果某组 prompt 明确要求“只输出简短解答”，而其他组没有相同要求，必须另加等价的简短提示控制组，避免把单纯的输出长度指令误当作 Skill 收益。

## 8.4 API 预算

本轮真实实验设定一个小规模上限：

- 最多约 3 个候选 Skill 家族；
- 每家族约 10～12 道独立 eligible 开发题；
- 三组配对比较；
- 核心解题调用目标不超过 108 次；
- 包括必要的额外调用后，总新增 LLM 调用最多 120 次；
- 总新增 token 预算上限 200,000。

这些是本轮实验的硬预算上限，而不是必须耗尽的额度。

运行前用现有日志估算实际成本；如预计会超出预算，应缩小样本或停止并报告，不得自动突破。

如果已经发现某个 Skill 明显无效或不符合数学正确性要求，不必将其预算全部花完。

## 8.5 必须记录每一次请求

至少包括：

```text
run_id
task_id
subject
difficulty
method
macro_id
macro_type
trigger_match
guard_pass
execution_attempted
execution_verified
fallback_reason
prompt_hash
input_tokens
output_tokens
total_tokens
api_call_count
latency
answer
offline_correct
parse_status
truncated
gold_exposed
```

还需记录宏策略中的确定性计算及验证耗时。

如果 API usage 缺失，应标记为 unknown 或 estimated，不能默认记零。

## 8.6 主要评价指标

**Correctness**

- 每组正确题数；
- 每组正确率；
- 逐题正负迁移；
- 因截断而失败的题数。

**Tokens**

- 输入 tokens；
- 输出 tokens；
- 总 tokens；
- 每题平均 tokens；
- 每成功题平均 tokens；
- 路由和额外调用成本。

**Reuse**

- Eligible 数量；
- 实际使用数量；
- 真正调用可执行算子的数量；
- 通过数学验证的数量；
- 直接完成整题的数量；
- 需要 LLM fallback 的数量。

**Generalization**

检查新题是否与来源题在表面形式上有实质差异，而不是简单改变数字或变量名。

# 九、Stage 7：逐题归因与净节省分析

不能只比较三组总体正确率。

必须建立逐题配对数据。

例如：

| 同一道题 | NoBank | Compact | Executable |
|---|---|---|---|
| Task A | 正确 | 正确 | 正确 |
| Task B | 正确 | 错误 | 正确 |
| Task C | 错误 | 正确 | 正确 |

统计每种路线：

- Base 错，Skill 对；
- Base 对，Skill 错；
- 两者都对；
- 两者都错。

并计算每道题的 token 差异。

## 9.1 特别分析输出 tokens

当前我们真正关心的是：

**Skill 是否减少模型为完成同一道数学题所需的生成计算？**

需要区分：

1. 输入 prompt 变短；
2. 输出推理变短；
3. 模型调用次数减少；
4. 数学计算被确定性程序替代；
5. 由于输出截断造成的表面正确率变化。

如果某个 Skill 只是多了一段提示，但输出长度不变或更长，就不能声称已经实现推理复用。

如果输出变短但错误率明显升高，也不能视为成功。

## 9.2 计算每个宏策略的实际收益

至少统计：

```text
macro_id
source_trace_count
eligible_dev_count
actual_uses
correct_without_macro
correct_with_macro
input_token_difference
output_token_difference
total_token_difference
build_cost
validation_cost
estimated_break_even_uses
```

同时记录置信区间或重采样的不确定性。

不要根据十几道题的微小差异，宣称已经证明准确率非劣。

## 9.3 摊销分析

统计建库和实验成本：

- 已有轨迹获取成本；
- 新增结构挖掘成本；
- 宏策略生成成本；
- 验证成本；
- 实际解题成本。

分别报告：

**Solve-only token saving**

和

**Amortized net token saving**

如果本轮只在一小批 eligible 题上发现节省，必须结合该策略在更广任务分布中的覆盖率来估算整体价值。

不能把“在选中的十几道题上每题节省 500 tokens”直接解释为“全部 MATH 题平均节省 500 tokens”。

# 十、下一轮继续或停止的决策

本轮应设置明确的 Go/No-Go 判断。

## 10.1 可以继续的情况

至少发现一条宏策略：

- 具有可观察的跨题适用范围；
- 在不同于来源题的独立开发题上能够实际使用；
- 没有发现无法接受的数学正确性问题；
- 有重复出现的 token 净节省信号；
- 能够解释节省来自哪里；
- 具有合理的未来覆盖率和摊销前景。

此时可以建议进入下一轮更大规模验证。

## 10.2 应停止并重新考虑的情况

如果：

- 能找到的高频数学结构都很笼统；
- 宏策略提示只能增加输入；
- 可执行操作仅覆盖极少量简单题；
- 整体输出 token 没有减少；
- 建库成本显著高于预期可摊销收益；
- 观察到明显负迁移；
- 或所有收益都由截断或 prompt 格式差异造成；

则应如实报告。

不能为了完成任务而强行激活 Skill、扩大题目数量或进行额外 prompt 调参。

特别重要：

**如果自然语言 Thought Skill 的路线仍然无法带来净节省，应单独评估“数学工具/执行程序替代计算”路线是否有价值，而不是继续无限增加策略提示长度和数量。**

# 十三、硬性要求与最终停止条件

本轮必须遵守：

1. 优先复用已有真实成功轨迹。
2. 不使用测试集 gold 训练或反馈给 solver。
3. 不修改历史实验结果。
4. 不把字符串关键词相似当成数学套路相似的充分证据。
5. 不把已检索 Skill 当成有效复用。
6. 不把局部计算验证当成整题正确。
7. 不把输入提示缩短直接称为推理压缩。
8. 不把非显著结果解释为已证明正确率非劣。
9. 不因候选数量不足而强行创造宏策略。
10. 不因试验效果不好而放宽实验协议。
11. 新增 LLM 调用不得超过本轮预算。
12. 不启动完整 MATH-500。
13. 不自动进入下一轮大规模实验。

最终完成：

- 轨迹审计；
- 重复数学结构挖掘；
- 候选筛选；
- 宏策略实现；
- 离线测试；
- 满足条件后的小规模真实模型验证；
- 成本与机制归因；
- 报告和数据交付。

到此停止，等待下一步科研决策。

**本轮最终目的不是做出更高的总体正确率，而是找到至少一种真正可以跨题复用、具备合理覆盖率、能够替代部分昂贵模型推理的数学宏策略。**

请现在从已有 Flowevo-Bot 仓库和历史轨迹开始实际执行，不要仅输出计划。若无法可靠发现具备复用价值的宏结构，应提供证据并明确停止，而不是继续消耗 API 寻找偶然的正向结果。
