# FlowEvo 下一阶段研究指引：反事实驱动的推理压缩与最小充分推理状态发现

## 一、总体目标

请继续在现有 GitHub 仓库 `https://github.com/ChenKaichen-SCUT/Flowevo-Bot` 中开展研究，以当前最新版本为基础，复用已有 FlowEvo 数学求解器、MathEvaluator-V3、真实模型响应、token 账本及实验验证代码。首先核对本地 HEAD、远端提交和历史文件，保留所有已完成的实验。

本轮只研究 **Counterfactual-Guided Reasoning Compression（反事实驱动的推理压缩）**，目标是在不明显损害数学解题正确率的条件下，减少 DeepSeek Flash 实际消耗的推理 tokens。

此前在 AFlow 公开的 605 道数学题上，已有：

| 方法 | 复核确认正确 | 总 tokens |
|---|---:|---:|
| 单次 2,048-token 上限 | 328/605 | 687,195 |
| 单次 16,384-token 上限 | 597/605 | 1,068,216 |

注意，两组是独立生成的回答，不能把低预算输出当成高预算输出的真实前缀。597 道正确来自数学复核，而不是全部经过独立形式化认证。

本轮核心研究问题为：

**RQ1：高预算正确解答中，是否存在大量对最终数学正确性没有必要的推理？**

**RQ2：能否通过反事实干预，找到模型在哪些中间状态已经具备正确完成题目的能力？**

**RQ3：这些状态是否具有可观察的共同特征，从而能够在不知道标准答案的情况下被识别？**

**RQ4：能否将这种识别方法用于实际推理，使总 token 成本下降，而不仅仅是在离线记录中删除一段文本？**

本轮不重新设计 Skill Bank，不开展通用数学工具扩充，也不引入其他领域的求解框架。研究始终围绕 LLM 推理轨迹、推理状态、答案形成、反事实干预和实际 token 消耗展开。

## 二、Stage 1：零 API 的历史推理轨迹分析

首先使用现有 605 道题的真实记录，核实 2,048 与 16,384 两组完整数据是否齐全。

对齐 task ID，并统计：

- 输入 tokens；
- reasoning tokens；
- 最终回答 tokens；
- 总 tokens；
- 输出完成状态；
- 最终正确性；
- 是否截断；
- 正确题和失败题的生成长度分布；
- 两种预算下相同题目的正确性变化。

如果 API 不提供某个精确 token 子项，应标记 unavailable，不能通过字符数冒充精确计费 tokens。

特别分析：

1. 高预算正确、低预算失败的题；
2. 高低预算均正确的题；
3. 两组均失败的题；
4. 高预算正确且实际推理特别长的题；
5. 高预算正确、但可见推理中出现多次重复检查的题。

对高预算成功轨迹，尽可能识别以下事件：

**Candidate Formation：** 第一次出现与题目目标相符的候选答案。

**Candidate Revision：** 后续改变、推翻或修正先前候选答案。

**Useful Verification：** 后续推理确实增加了有效的数学证据、纠正了计算或发现遗漏条件。

**Redundant Reasoning：** 后续重复相同论证，没有观察到新的数学信息。

**Finalization：** 模型最终形成并提交正式答案。

不能因为出现一个与 gold 相同的数字，就认定该时刻已经足以安全结束推理。需要结合目标类型、约束和后续推理变化进行分析。

对于推理状态不可见或记录不完整的任务，必须标记不可观察，不得臆测。

生成 `01_TRACE_ANALYSIS.md`、`trace_alignment.csv`、`reasoning_events.jsonl` 和 `token_length_distribution.csv`。

## 三、Stage 2：反事实推理截断实验

这是本轮最重要的研究环节。

我们需要检验：

**如果模型在历史正确轨迹的某个中间位置停止继续原有推理，转而立即完成答案，是否仍然能够解对？**

不能只将历史完整推理的后半部分删除，然后直接声称节省了这些 tokens。

必须通过真实模型调用，验证干预后的结果。

### 3.1 选择实验任务

从已有轨迹中选择具有代表性的样本：

- 一部分长推理且最终正确的题；
- 一部分曾修改错误候选后才正确的题；
- 一部分存在明显重复验证的题；
- 一部分实际需要较长计算才能正确的题。

必须包含负面控制案例，防止算法只在“早就找对答案”的题上表现良好。

本轮首先选择约 20～30 道具有完整、可用推理记录的任务进行反事实研究。历史题只用于机制发现，不得将结果作为独立泛化成绩。

### 3.2 构造推理状态

对同一条真实推理轨迹，尝试在不同进度位置构造状态，例如：

- 约 25%；
- 约 50%；
- 约 75%；
- 首次出现候选答案之后；
- 一次关键数学检查完成之后。

优先在完整数学步骤或语义边界处截取，不要从 LaTeX 表达式或公式中间机械切断。

必须记录截取位置、可见文本、预计已生成 tokens 和对应的数学状态。

这些截取位置仅用于离线研究。实际在线算法不能根据 gold 选择最好的截断点。

### 3.3 反事实干预

对于每个可用状态，至少比较：

**A：正常继续推理**

让模型在相同可用上下文下继续分析，并提交答案。

**B：立即完成答案**

要求模型利用当前已经形成的推理内容，尽快输出最终答案，不再无目的地重新推导整道题。

**C：简短必要验证后完成答案**

只允许模型检查关键数学条件、必要的运算与题目目标，然后提交答案。

三种干预应使用相同的题目和可用状态信息，保持可比较的模型配置。

必须首先检查 DeepSeek API 是否支持把真实 reasoning 状态作为可合法续接的上下文。

如果只能通过普通 Prompt 重新提供历史片段，应明确标记为 `text_prefix_reprompt`，不能将其冒充原始模型内部状态的无损续接。

如果 API 根本不支持可靠状态续接，也应如实报告限制，并将实验定位为“推理文本状态的反事实再提示”，不能据此证明在线提前停止能够直接实现。

### 3.4 评价反事实结果

对每个状态和干预记录：

- 是否生成完整最终答案；
- 数学正确性；
- 是否改变原先候选答案；
- 是否遗漏重要约束；
- 是否出现新错误；
- 额外输入和输出 tokens；
- 实际调用次数；
- 是否属于有效压缩。

离线可以使用 gold 评价不同干预，但不允许将 gold 或正确性标签传给模型。

对于某条历史轨迹，最早能够成功完成的位置可以作为**反事实 oracle 上界**，不能作为在线方法的实际性能。

特别分析：

**有多少题可以提前完成？**

**有多少题提前完成会失去正确性？**

**是否存在某些数学状态，继续推理反而更容易改变已经正确的答案？**

不能只展示成功提前结束的案例。

## 四、Stage 3：发现最小充分推理状态

根据真实反事实实验，研究哪些数学与语言特征能够预测当前推理已经具备正确完成的条件。

候选特征可以包括：

- 是否形成了明确的目标答案；
- 候选答案在最近多个推理步骤中是否保持稳定；
- 是否完成了必要的数学约束检查；
- 是否存在尚未处理的定义域或边界条件；
- 是否出现连续重复的推理；
- 最近的推理是否产生新的数学事实；
- 模型是否已经获得足够信息回答原始问题；
- 后续推理是否曾经纠正先前错误。

需要明确区分：

**候选答案已经出现**和**当前状态足以可靠完成题目**。

这两个条件不等价。

请建立结构化的 `ReasoningState`，至少记录当前候选答案、已完成的关键步骤、未解决的检查事项、可观察的重复信息和状态证据。

在历史训练/开发记录中，可以借助反事实结果学习哪些状态具有提前完成潜力。

但实际在线判断只能使用截至当前时刻已经观察到的信息，不能读取未来推理、最终 gold 或事后正确性。

不要一开始就训练复杂的神经网络。先使用简单、透明的特征和决策规则，判断这些特征是否真的具有预测能力。

生成：

- `03_MINIMAL_SUFFICIENT_STATE.md`
- `reasoning_state_features.csv`
- `counterfactual_outcomes.jsonl`
- `early_completion_risk.csv`

特别回答：

**是否存在一种跨题的状态特征，比单纯依靠推理长度、候选答案首次出现或重复文本更可靠？**

如果没有，应明确报告，不要强行构造复杂算法。

## 五、Stage 4：设计最小在线推理压缩原型

只有前三阶段发现明确积极证据，才进入本阶段。

实现一个最小版本的 Counterfactual-Guided Completion Controller。

其目标是：

**在某个可观察状态满足充分完成条件时，安全地产生最终答案，避免继续进行不必要的推理。**

必须先完成 API 可行性审计：

1. 是否能够实时观察生成中的相关推理状态；
2. 是否支持流式输出；
3. 是否能够可靠终止请求；
4. 提前终止后如何获取最终答案；
5. 是否支持从已有状态继续；
6. 如果必须再次调用模型，需要多少额外 tokens；
7. 取消请求后的实际计费如何记录。

**如果无法在生成过程中取得必要的在线状态，或者不能实现可靠的答案完成流程，不得将离线模拟器宣传为实际 token 压缩系统。**

允许采用一个工程上真实可行的替代方案，例如显式阶段化生成与检查，但必须计入检查、状态传递、二次调用及其他全部开销，并与同样阶段化的简单规则对照。

### 5.1 基线比较

至少保留：

**B0：** DeepSeek Flash 单次 16,384-token 高预算。

**B1：** 只根据生成长度或固定阶段决定结束。

**B2：** 发现候选答案后尝试结束的简单规则。

**B3：** 基于文本重复或推理收敛的简单规则。

**B4：** 本轮反事实结果指导的状态判断机制。

必要时增加简洁回答 Prompt 作为工程基线，防止新机制收益只是来自“要求模型写短一些”。

保持相同基础模型和可比较的最大生成预算。

### 5.2 不允许的归因

不能把：

- 删除历史日志中的 tokens；
- 离线选择最短正确轨迹；
- 使用 gold 选出最优截断点；
- 仅比较后续生成 tokens 而忽略前缀成本；
- 减少最终答案文字但保留原推理成本；

当作真实的在线推理成本节省。

必须测量完整端到端实际计费 tokens。

## 七、Stage 6：机制归因与后续研究判断

最终必须回答：

**RQ1：是否存在真实的可压缩推理空间？**

例如，在多个不同数学任务中，反事实实验能否证明省略后续部分推理，依然可以正确完成任务？

**RQ2：是否能够在线识别？**

离线最早成功结束的位置，与实际控制器决定结束的位置相差多少？

**RQ3：压缩是否真正发生？**

实际减少的是计费 tokens，还是只删掉了日志文本或把计算转移到新的调用中？

**RQ4：是否优于简单提前结束？**

新机制相对于固定长度、首次候选、简单重复检测等规则是否有增量贡献？

**RQ5：是否损害正确率？**

在哪些数学任务中，提前结束会删除真正必要的推理？控制器能否识别并避免？

### Go / No-Go 标准

**GO：** 在多个具有实质差异的独立数学题上，观察到可复现的真实 token 净节省，没有明显正确率负迁移，并且反事实驱动状态机制优于简单规则。

**PARTIAL：** 反事实实验发现大量可省略推理，但在线识别或实际实现还不可靠。

**NO-GO：** 历史推理看起来冗长，但受控干预经常使正确率下降；或者实际在线成本未低于高预算单次求解及简单早停基线。

不允许通过不断改变阈值、选题或 Prompt 来强行得到正向结果。
