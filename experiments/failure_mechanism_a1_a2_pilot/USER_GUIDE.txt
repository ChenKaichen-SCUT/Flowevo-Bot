# FlowEvo 下一阶段研究指引：数学失败机制分析、答案完成控制、目标一致性与高预算单次生成

## 一、研究背景和总体目标

请继续基于现有 GitHub 仓库：

https://github.com/ChenKaichen-SCUT/Flowevo-Bot

开展下一阶段科研实验，以已完成的 MathEvaluator-V3 提交 `f0afc2c8af5be165b36c05a168b2f320d08de3c1` 为参考起点。首先核实本地 HEAD、实际代码版本、历史结果和可用数据，禁止覆盖历史实验。

本次研究的主要目标已经从减少 token 改为**提高数学题目的真实解题正确率**。

此前两批 MATH-500 实验显示：

- 修正评分和提供更大生成预算后，DeepSeek Flash 可以解决绝大多数题目。
- 最近一批 500 题中，固定预算 V3 自动确认 466 题，自适应预算 V3 自动确认 495 题。
- 最后未自动确认的 5 题，包含 1 道正确但评测器 Unknown、3 道未完成输出以及 1 道真正的答案目标错误。
- 历史失败中出现了已经推导出关键答案却迟迟不提交、反复推敲直至截断，以及计算过程正确但最终回答偏离题目目标等现象。
- 这些现象目前只有少量案例，尚未证明具有跨题普遍性。

本轮研究三个方向：

**RQ1：失败机制是否具有跨题普遍性？**

通过已有完整解题记录，识别过度推理、答案未提交、目标漂移和题意歧义等问题，判断哪些是重复出现的失败机制。

**RQ2：直接提高初始生成预算是否优于当前分级重新生成？**

比较单次 16,384 tokens 与 `4,096 → 8,192 → 16,384` 的分级重试，在正确率、完成率、调用次数和实际 token 消耗上的表现。

**RQ3：A1/A2 是否能进一步提升正确率？**

A1 为 Answer Finalization，即检测候选答案已经形成但尚未提交的状态，尝试安全地完成答案。

A2 为 Goal Consistency，即检查模型最终回答的对象、目标、约束是否仍然与原题一致。

本轮不再引入 BoT、数学 Skill Bank、Recovery Memory 或 gold-answer reflection。

## 二、Stage 0：冻结环境与检查 API 行为

在新增任何模型调用前，检查 DeepSeek Flash 的当前 API 能力。

重点确认：

1. `max_tokens` 是生成上限，而不是固定消耗额度。
2. `reasoning_content` 和最终 `content` 如何返回。
3. `finish_reason` 的实际含义。
4. 推理 tokens 是否计入 output tokens。
5. 是否支持流式获取推理内容及最终回答。
6. 能否在生成期间观察到候选答案。
7. 是否支持暂停、取消或继续生成，取消后是否会丢失模型内部状态。
8. `reasoning_effort`、thinking mode、`top_p` 等实际影响生成过程的参数。

**不能假设中断请求后可以原样继续内部推理。**

如果 DeepSeek API 不支持保留推理状态，那么 A1 必须采用真实可实现的方式，例如从已经暴露的候选答案中形成最终提交，或通过额外请求完成答案；不能伪造“继续原推理”的能力。

检查当前推理配置，保留：

- DeepSeek Flash；
- Gold feedback OFF；
- Skill injection OFF；
- API 全局最大并发 64；
- 本地最大并行 12；
- 相同基础 Prompt；
- 相同思考模式与推理强度；
- 相同 MathEvaluator-V3 离线评分口径。

若 V3 存在 Unknown，应单独记录，不能直接当成数学错误。

## 三、Stage 1：零新增 API 的完整失败机制图谱

**本阶段禁止新增任何付费 LLM 调用。**

利用过去两批 MATH-500，以及截断恢复、失败恢复和不同生成预算实验中的历史请求记录，建立失败机制数据集。

不要只检查最终失败题。

还需要分析：

- 曾经截断、后来成功的题目；
- 首次完整正确的题目；
- 首次未完成但推理中出现过关键候选答案的题目；
- 不同预算下推理内容和完成状态变化明显的题目；
- 曾经出现数学目标误解的题目。

### 3.1 建立失败类型

至少包括：

**F1：Answer Found but Not Finalized**

模型在可访问的推理记录中已产生合理候选答案，但随后反复检查，没有提交完整最终回答。

**F2：Repeated Reasoning / Verification Loop**

模型不断重复实质相似的推理或检查，没有形成新的数学信息，最终耗尽预算。

**F3：Goal Drift**

模型正确完成了一部分计算，但最终回答的数学对象不是题目要求的对象。

例如要求连续四个整数之和，却回答符合条件的起点之和。

**F4：Constraint Drift**

推理过程中遗漏或改变了题目的定义域、取值条件、变量要求、单位、量词或其他约束。

**F5：Ambiguous Problem Semantics**

模型反复质疑题意；离线审查也发现题目、参考答案或数学语义确实不明确。

**F6：True Mathematical Error**

模型给出完整答案，但存在可以明确确认的数学错误。

**F7：Evaluator / Interface Failure**

模型实际上已经交付正确答案，却未被正确提取或评分。

**F8：Unknown**

当前证据不足，无法可靠确定原因。

允许一题具有多个标签，但需要区分主要原因和辅助原因。

### 3.2 失败机制必须有证据

每一道候选案例必须保存：

- 题目 ID、学科、难度；
- 原始题目；
- 推理预算；
- 原始最终回答；
- 可访问的推理内容或其证据位置；
- 是否真正产生最终答案；
- 是否截断；
- 推理中首次出现候选答案的位置；
- 是否出现重复检查；
- 是否发生数学目标变化；
- 离线数学正确性；
- 失败类型和判断依据。

如果 API 没有提供完整推理内容，必须标记为不可观察，不能根据输出猜测内部思考过程。

对于“模型其实已经找到正确答案”的判断，离线分析可以在生成完成后使用参考答案核验；但未来在线 A1 控制器不能借此获得 gold。

### 3.3 统计失败现象的覆盖范围

除了列出典型例子，还应统计：

- 每类现象出现多少题；
- 有多少题最终失败；
- 有多少题最终成功；
- 各类现象是否集中在特定学科；
- 是否集中在较长推理中；
- 是否能够通过 API 实际可观察的信号识别；
- 是否只有离线审计才能发现。

特别计算这些现象在**所有已审计题目中**的比例，不能只使用失败题作为分母。

最终输出：

- `01_FAILURE_MECHANISM_ATLAS.md`
- `failure_taxonomy.csv`
- `failure_cases.jsonl`
- `repeated_reasoning_cases.jsonl`
- `goal_drift_cases.jsonl`
- `online_observable_features.csv`

明确回答：

**A1 和 A2 所针对的问题究竟有没有足够多的真实案例，值得继续研究？**

## 四、Stage 2：优先研究直接高预算与分级重试

这项实验必须在 A1/A2 的性能归因中作为强基线。

此前默认使用：

```text
4096
  ↓ 未完成
8192，从头生成
  ↓ 未完成
16384，再次从头生成
```

但每次重新生成都需要重新消耗 tokens。

因此有必要比较：

### B0：固定低预算

`max_tokens = 4096`

只求解一次。

### B1：分级重新生成

首次 4,096；未完成时升级至 8,192；仍未完成则升级至 16,384。

### B2：直接高预算

首次就设置：

`max_tokens = 16384`

正常生成完成即结束。

不因为请求上限较大而要求模型使用全部预算。

建议额外考虑 `max_tokens=8192` 的直接生成条件，用于了解是否需要一开始就设置 16,384，但不能无限增加预算档位。

### 关键研究问题

1. 直接高预算是否提高完整答案交付率？
2. 是否比分级重试减少总模型调用？
3. 是否消除重复计算造成的 token 浪费？
4. 直接高预算是否导致过度思考更频繁？
5. 模型实际输出 tokens 是否会随生成上限明显增长？
6. 哪些题目仅在直接高预算条件下成功？
7. 哪些题目反而在分级重试中成功？

注意：两种方式的独立调用会产生不同推理轨迹。必须报告采样随机性的影响，不能将单次差异全部归因于预算设置。

**如果 B2 正确率不低于 B1，且实际成本更低，则后续原则上使用 B2 作为 A1/A2 的主要基线。**

如果 B1 在准确率上具有明确优势，则分析重新采样和多次求解带来的潜在收益。

不要预先断言哪种方法一定优越。

## 五、Stage 3：实现 A1——Answer Finalization

A1 的目标不是压缩所有数学推理，而是解决：

**模型已经形成可用的候选答案，却因为重复检查、迟迟不提交或生成预算耗尽而失败。**

### 5.1 候选答案识别

从模型实际可观察的信息中，识别：

- 是否已经出现与原题目标相关的候选结果；
- 候选结果是否具有完整数学类型；
- 是否具备可以检查的数学约束；
- 是否持续重复同一候选结果；
- 是否已经进入没有明显新信息的重复验证状态。

可以复用 MathEvaluator-V3 中的数学解析能力，但不得访问当前题目的标准答案。

如果无法确认候选结果与原题目标一致，不得直接提交。

### 5.2 答案完成策略

根据 API 的真实能力，选择可执行方案。

例如：

**方案 A：候选答案安全提取。**

当模型已经通过可见输出提交完整候选结果，并且有足够的可观察数学证据时，检查它是否满足题目目标，必要时将其整理为最终回答。

**方案 B：受控最终回答请求。**

当某次生成未完成，但可用输出包含候选结果时，使用额外的短请求要求模型根据已知题目和合法上下文提交最终答案。

必须记录额外请求的 token 成本。

**方案 C：流式完成检查。**

如果接口真正支持流式观察和可靠中止，可以研究何时结束生成。

但不得将普通取消请求宣称为“保留推理状态的即时最终回答”。

### 5.3 防止提前结束

A1 可能存在新的风险：

模型刚产生一个错误的中间答案，就被系统提前结束。

因此必须记录：

- 候选识别次数；
- 触发完成次数；
- 正确提前完成次数；
- 错误提前完成次数；
- 原本会正确完成却被提前打断的次数；
- 触发时间和额外成本。

A1 不能只是简单添加一句“请尽快回答”，需要证明它在有充分证据的情况下，能够比普通提示或高预算求解更可靠地完成答案。

## 六、Stage 4：实现 A2——Goal Consistency

A2 主要针对数学目标漂移问题。

它的任务不是重新求解整个问题，而是检查：

**模型当前准备提交的答案，是否仍然回答原始问题。**

### 6.1 结构化目标

从原始题面提取 GoalSpec，至少包含：

```text
target_object
target_operation
target_variables
domain_constraints
quantity_constraints
answer_cardinality
unit_requirements
required_output_type
```

例如：

题目要求“四个连续整数的和”。

GoalSpec 应保留：

- 对象：四个连续整数；
- 操作：求和；
- 输出：一个数值。

不能将目标误变成“满足条件的起点数量或起点之和”。

### 6.2 Goal Consistency Checker

对比原始 GoalSpec 和模型最终答案对应的目标结构。

重点检查：

- 是否回答正确变量；
- 是否求了题目要求的数学量；
- 是否遗漏部分解；
- 是否改变求和、求积或计数对象；
- 是否把中间结果当成最终结果；
- 是否违反单位或定义域；
- 是否把存在性问题变成求值问题。

该检查只依赖题面和模型输出，不依赖 gold。

### 6.3 发现问题后的处理

如果发现高可信度目标不一致，可以要求模型依据原题目标修复最终答案。

如果数学目标解析本身不确定，应当保守处理，不要强制修改已经正确的模型答案。

### 6.4 必须评估负迁移

特别检查：

- 原本正确答案是否被 A2 错误修改；
- GoalSpec 是否错误理解题目；
- 是否引入更多模型调用；
- 是否只是通用“重新检查题意”提示带来的效果。

增加一个简单对照：

**Generic Goal Reminder**

仅在最后提醒模型重新确认题目要求，不使用复杂的结构化 GoalSpec。

只有 A2 优于这个简单对照，才有理由认为结构化目标一致性检查具有独立价值。

## 七、Stage 5：在独立开发题上进行小规模验证

前面两批 MATH-500 和历史失败案例已用于发现机制，不能再把它们当成全新独立验证集。

本轮应从未用于 A1/A2 设计的任务中建立一个新的开发验证集。

建议包含：

- 一部分较难数学题；
- 一部分一般难度数学题；
- 不同学科和解题结构；
- 足够多的完整正确题，用于检测负迁移。

优先选择约 40～60 道独立题作为小规模探索性实验，根据可用数据和预算调整。

不允许仅挑选已经知道会出现过度推理或目标漂移的题目来报告整体正确率。

### 7.1 核心对照

至少包含：

| 方法 | 目的 |
|---|---|
| B0 固定 4,096 | 原始低预算基线 |
| B1 分级预算重试 | 当前已验证机制 |
| B2 直接 16,384 | 用户提出的更简单强基线 |
| B2 + A1 | 检验答案完成控制 |
| B2 + A2 | 检验目标一致性 |
| B2 + Generic Goal Reminder | 排除简单自检提示带来的收益 |

如果 A1、A2 分别出现正向证据，再试验 B2 + A1 + A2 的组合，不要一开始就用组合机制掩盖各自的作用。

对于有条件触发的分支，应尽可能复用冻结的共同初始请求，保证归因清楚。

### 7.2 API 与预算

继续沿用：

- DeepSeek Flash；
- API 最大并发 64；
- 本地计算最大并行 12；
- Gold feedback OFF；
- Skill injection OFF；
- 禁止根据 gold 自动重试；
- 相同基础 Prompt；
- 冻结 MathEvaluator-V3 评测配置。

本轮先按最多约 200 次新增正常模型调用、1,500,000 实际 tokens 设定试验安全上限。开始前必须根据任务数与预算档位计算成本预测，如预计超限，先缩小样本；实际运行达到上限则安全停止并报告未完成情况，不得自动扩展。

不运行完整新的 MATH-500。

### 7.3 逐题记录

至少记录：

```text
task_id
subject
level
method
model
reasoning_effort
requested_max_tokens
finish_reason
reasoning_tokens
final_content_tokens
total_input_tokens
total_output_tokens
all_attempt_tokens
api_call_count
candidate_detected
candidate_detection_evidence
finalization_triggered
goal_spec
goal_mismatch_detected
goal_repair_triggered
final_answer
answer_complete
offline_correct
evaluator_status
```

每个字段必须对应真实记录。

如果 API 没有提供某种 token 明细或推理状态，标记 unavailable。

### 7.4 逐题比较

必须给出：

- B2 比 B1 多做对多少题；
- B2 比 B1 少做对多少题；
- A1 相比 B2 新救回多少题；
- A1 是否破坏原本正确的题；
- A2 相比 B2 新救回多少题；
- A2 是否破坏原本正确的题；
- 普通目标提醒是否已经取得类似收益；
- 各方法实际 token 与调用成本。

小样本主要用于寻找机制信号，不能据此宣称已证明严格的正确率非劣或统计显著提升。

## 八、Stage 6：分析机制是否真的解决一类失败

不要只统计总正确率。

必须为 A1 和 A2 分别回答：

### A1

1. 是否在新题中再次观察到答案已形成但未及时提交？
2. 在线能否真正识别这一状态？
3. A1 是否救回了这类题？
4. 是否发生错误提前终止？
5. 直接 16,384 是否本来就能解决这些题？
6. A1 比直接高预算提供了什么新增能力？

### A2

1. 是否在其他题中发现目标漂移？
2. 结构化 GoalSpec 能否正确定位目标？
3. A2 是否实际纠正错误回答？
4. 是否错误修改正常答案？
5. 是否优于简单的目标检查提示？
6. 目标漂移是否具有足够高的发生率，值得使用额外控制机制？

对于失败案例，要说明为什么失败，不能只报告数字。

尤其强调：

**如果 A1/A2 的提升仅来自额外模型调用或更长 Prompt，而同预算简单基线取得相同收益，就不能认为新机制具有独立价值。**

## 九、Go / No-Go 判断

本轮分别对三个研究问题给出结论。

**直接高预算：GO**

如果 B2 在正确率上不低于 B1，且调用更少、token 成本更合理，则建议替换原有分级重试作为主要数学求解基线。

**A1：GO**

需要在多道不同来源的新题中重复观察到可在线识别的答案完成问题，并且 A1 能够以合理代价救回这些题，而不明显破坏正常题。

**A2：GO**

需要在多道新题中观察到可复现的目标漂移，且结构化检查能够在不知道 gold 的情况下纠正错误，并优于简单目标提醒。

如果证据不足，标记 PARTIAL。

如果机制无法超过直接高预算或强简单对照，标记 NO-GO。

不要为了获得 GO 而更改数据、阈值、预算或评分标准。
