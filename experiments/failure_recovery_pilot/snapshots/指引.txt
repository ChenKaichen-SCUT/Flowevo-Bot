# FlowEvo-Recovery：失败诊断、自适应推理与跨任务纠错经验的小规模可行性实验

## 一、总体目标

请基于现有 GitHub 仓库：

https://github.com/ChenKaichen-SCUT/Flowevo-Bot

开展下一阶段科研实验。参考最新已完成的 V4 提交：

`eba3d76c8418ea28173004b2f46e51c3856b0643`

首先核对实际代码、历史实验、数据和配置，确认现有工作状态。

本次研究方向正式从 **FlowEvo + BoT 成功解题套路复用** 转为 **FlowEvo + Failure-Aware Recovery**。

请在现有仓库中新建独立模块 `FlowEvo-Recovery`，以关闭 gold-answer feedback 的 FlowEvo 数学/代码运行流程为基础，优先复用已有评测器、逐请求日志、token 账本和代码执行环境。

不再把 BoT Thought Distiller、自然语言 Skill Bank 或自动数学宏合成作为新系统的核心。保留它们的历史源码与结果，不得删除或覆盖。

本轮只进行**小规模可行性研究**，不直接构造复杂的正式算法，不运行完整 MATH-500，不开展大规模参数搜索。

### 需要回答的三个研究问题

**RQ1：DeepSeek Flash 为什么没有解出部分数学和代码题？**

这些失败主要来自随机采样、输出截断、局部推理错误、遗漏约束、算法或解题思路错误，还是模型当前能力不足？

**RQ2：方向 A 是否值得研究？**

能否仅利用当前解题过程可观察的信号，判断什么时候值得追加计算，以及应当采用哪种恢复操作，从而比固定重试策略救回更多题，或在相近准确率下节省 tokens？

**RQ3：方向 C 是否值得研究？**

能否从其他任务上经过验证的失败恢复经验中，学习“什么失败状态对应什么恢复方式”，并在新的数学/代码任务中取得比不使用经验的自适应控制器更好的结果？

三个问题必须独立评价，不能因为某种重试方式偶然答对几道题，就宣布跨任务经验学习有效。

## 二、第一阶段：审计历史失败任务

首先复用已有真实实验数据，不要立刻启动 API。

历史上 DeepSeek Flash 的相关结果包括：

- MATH 500：Bot-NoBank 正确 464/500，错误 36 题。
- 代码任务 500：此前有约 28 道最终失败题，但必须重新核对其实际配置和 gold-free 状态。
- FlowEvo 早期实验存在 gold-answer reflection 问题，不能直接将相关恢复记录视为合法的自主纠错案例。

请找到真实的逐题数据，确认哪些记录可以作为可信的首次解题结果。

对于历史 MATH-500 的 36 道失败题，以及代码任务中能够确认的失败题，先进行回顾性诊断。

这些题目已经被我们研究过，只能用于**探索和发现现象**，不能用于后续独立确认新算法性能。

### 2.1 建立失败原因分类

至少区分：

1. **Answer/Format Failure**：数学推导可能正确，但最终答案格式错误或解析失败。
2. **Truncation Failure**：推理尚未结束就达到输出上限。
3. **Local Calculation Failure**：思路基本正确，但局部运算、变形或代码细节错误。
4. **Constraint Failure**：遗漏定义域、边界情况、题目约束或隐藏条件。
5. **Strategy Failure**：选择了不合适的数学方法、算法设计或问题表示。
6. **Verification Failure**：候选解答与可观察的验证证据不一致。
7. **Insufficient Reasoning**：多次推理仍无法获得可靠解法。
8. **Evaluator/Environment Issue**：评分器、执行环境或题目规范存在问题。
9. **Unknown**：现有证据不足，不能确定失败原因。

允许同一题具有多个标签，但应区分主要原因和次要原因。

不能只凭一次失败轨迹就断言模型缺少某种知识。需要通过后续干预判断：模型是否有能力产生正确解法。

### 2.2 每道题必须提供证据

记录：

- task ID、学科/代码任务类型及难度；
- 原始题目；
- 原始解题轨迹；
- 原始最终答案；
- 离线判分结果；
- 是否截断；
- 是否存在可验证的局部错误；
- 失败步骤或失败位置；
- 失败类型和判断依据；
- 当前尚不能解释的问题。

失败原因可以在离线研究时参考 gold 答案，但必须明确：**这些离线标签及标准答案不能进入后续在线恢复控制器。**

输出一份真实失败案例集，不得使用编造示例。

## 三、第二阶段：设计小规模反事实恢复实验

本阶段的目的不是立即训练新策略，而是找出：

**同一个失败状态，在不同恢复操作下是否存在明显不同的结果。**

对于选出的失败题，冻结其首次解题结果，构造不同恢复分支。

至少比较以下操作：

| 恢复操作 | 实验目的 |
|---|---|
| Continue | 沿原来的推理路径继续，检查是否只是推理不足或截断 |
| Independent Retry | 不提供 gold，重新独立求解，检验采样本身能否救回 |
| Verify-and-Repair | 利用合法的局部验证、编译或公开测试信息，尝试定位并修复错误 |
| Replan | 明确要求采用不同的问题表示、数学策略或代码算法，检验原策略是否是主要瓶颈 |

数学题可使用合法的局部符号验证、代入检查、约束一致性检查，但不得依赖当前题 gold answer。

代码题可以使用公开测试、编译和执行结果，但不得在在线恢复期间查看隐藏测试答案或由隐藏测试生成纠错提示。

尽可能使各恢复分支拥有相同的额外模型调用预算。记录实际 token 开销，不能只比较成功率。

建议先从干净的训练/开发数据中选择：

- 数学失败题约 8～12 道；
- 代码失败题约 8～12 道；
- 另保留正确题作为后续误触发检查。

如果已有的合法失败数据不足，可以从尚未使用的训练/开发任务中生成首次解答，但需记录新调用及花费。

### 3.1 真正区分三类失败

实验后，尝试将失败任务划为：

**Recoverable by Resampling**

简单独立重试就可能得到正确解。

**Recoverable by Targeted Intervention**

普通重试失败，但某种特定诊断、修复或重新规划能够成功。

**Not Recovered under Tested Budget**

在本轮所有受限干预下都没有成功恢复。

注意，第三类不代表题目绝对无法被 DeepSeek Flash 解决，只代表在已测试策略与预算下没有恢复。

### 3.2 分析各恢复动作的因果贡献

对于每个冻结状态，记录各分支是否成功以及成本。

必须回答：

- 多少错误通过简单重试就能纠正？
- 多少错误需要特定反馈？
- 多少错误需要改变原来的解题思路？
- 哪些状态反复使用相同策略仍然失败？
- 哪种干预在何种失败类型下更有优势？
- 是否存在某种恢复方式系统性地产生新的错误？

可以离线统计“如果知道哪条分支正确，理论上最多能救回多少题”的 oracle 上界，但这仅用于研究分析。

**不得把离线 oracle 选出的最佳恢复分支作为实际系统的成绩。**

## 四、第三阶段：实现方向 A——Failure-Aware Controller

在前两阶段收集到证据后，开发一个最小版本的失败感知控制器。

它需要在没有 gold answer 的情况下，根据首次推理产生的可观察信息，决定：

1. 直接结束；
2. 继续原推理；
3. 独立重新尝试；
4. 执行局部验证并修复；
5. 改变解题策略重新规划。

第一版优先使用透明、可解释的规则，避免一开始训练复杂模型。

### 4.1 可以使用的信号

例如：

- 最终答案是否完整；
- 是否出现明确截断；
- 数学答案的局部代入或符号检查是否失败；
- 推理过程是否出现可检测矛盾；
- 代码是否通过编译；
- 代码是否通过当前允许使用的公开测试；
- 是否出现异常、类型错误或确定性约束违反；
- 当前失败类型是否存在可靠的自动诊断证据。

对于无法可靠验证的数学推理，不得把模型自报的“我很确定”当成已证明的正确性。

### 4.2 必须避免的情况

不能用真实 `correct/incorrect` 标签决定当前任务是否重试。

例如：

```text
if offline_correct == False:
    retry()
```

这是无效的测试阶段 oracle 策略。

实际 Controller 的输入必须来自模型可观察状态。

### 4.3 强确定性基线

必须比较：

- 原始 FlowEvo Gold-Free 单次求解；
- 固定追加一次独立重试；
- 仅在截断、编译失败或公开测试失败等确定信号出现时重试；
- Failure-Aware Controller。

尤其是代码任务，此前“公开失败才重写”已经是很强的简单基线。

如果新 Controller 不能优于这些基线，不能声称发现了新的自适应恢复机制。

## 五、第四阶段：实现方向 C——Recovery Experience Memory

这一阶段研究跨任务恢复经验。

**这里不再使用 BoT 的数学解题 Skill Bank。**

新的 Memory 保存的是经过验证的恢复决策经验。

建议每条记录包含：

```text
RecoveryExperience:
    task_domain
    observable_failure_features
    diagnostic_evidence
    initial_action
    intervention_action
    intervention_outcome
    additional_tokens
    confidence
    provenance
```

例如，记录的不是：

“这道代数题的答案是什么。”

而是：

“当推理输出被截断、尚未形成最终答案且没有发现明显前置步骤错误时，继续原推理相比完全重新求解是否更有效。”

或：

“当代码的公开测试出现某种边界错误时，先构造并检查最小反例，相比立即全面重写是否更有效。”

所有经验必须有真实任务、真实干预和真实结果作为来源。

不能保存测试题 gold、原题标准答案或特定任务完整解答供下一题检索。

### 5.1 学习过程

先从训练任务的反事实恢复分支中提炼记录。

根据：

- 可观察失败特征；
- 恢复动作；
- 成功与失败结果；
- 额外成本；

建立简单的经验选择器。

可以先采用结构化检索与经验统计，不必训练新的神经网络。

相似失败状态不一定需要相似恢复方式，因此要考虑负面经验和条件不匹配问题。

### 5.2 必须证明经验真的能够迁移

冻结 Recovery Memory 后，在没有参与记忆构建的新任务上验证。

至少比较：

**A：无经验的 Failure-Aware Controller**

仅使用本轮固定的诊断规则和恢复操作。

**C：加入 Recovery Experience Memory**

使用同样的诊断特征、恢复操作集合和预算，但根据以往验证过的经验调整动作选择。

可以增加：

**C-Shuffled：打乱恢复经验与失败状态的对应关系。**

这样能够检查收益是否来自真正的经验匹配，而不是额外 prompt 或随机变化。

必须保证 A 和 C 使用相同的恢复动作集合，不能给 C 增加 A 无法使用的新工具。

对于迁移，应优先检查不同 task ID、不同数值实例和不同解题结构的泛化。如果样本支持，再单独观察数学到代码等跨领域迁移；不能因为都是失败恢复就假定两领域的策略可直接迁移。

## 六、第五阶段：冻结后的小规模独立验证

本阶段只做一次小规模验证，目的是寻找值得进一步研究的信号。

优先从此前没有用于构建恢复经验的任务中生成新的首次解答。

建议形成：

- 数学首次失败任务约 8～12 道；
- 代码首次失败任务约 8～12 道；
- 数学首次成功任务约 8～12 道；
- 代码首次成功任务约 8～12 道。

失败题用于评估恢复潜力，成功题用于评估误触发、准确率损伤和额外成本。

**不能只挑模型已知答错的题计算整体准确率提升。**

必须区分失败子集恢复率与正常任务分布上的端到端效果。

如果无法获得足够新的独立任务，可以缩小试验，但要明确标注结论属于探索性证据，不能用历史 500 测试集冒充新的 holdout。

### 6.1 固定模型配置

继续使用：

- DeepSeek Flash；
- API 全局最大并发 64；
- 本地最大并行 12；
- gold-free；
- 与已有基线可比较的 temperature 和最大输出预算；
- 完整逐请求 token 记录。

正式比较前冻结 Controller、Memory、数据划分和实验配置。

每个方法原则上最多允许**首次解答之外的一次额外 LLM 恢复调用**。如果需要两次以上恢复，必须作为另外的预算档位，不能与一次重试基线直接混比。

### 6.2 本轮预算

本轮只允许小规模真实 API 实验：

- 新增 LLM 调用最多约 240 次；
- 新增总 tokens 不超过 300,000；
- 不运行完整 MATH-500；
- 不开展额外大规模调参。

这些是硬上限，不要求全部使用。

模型基础设施重试必须与主动推理恢复区分统计。

若预算不足以完成全部分支，应优先保留强基线与 A/C 配对，并记录未完成部分。

## 七、最终必须回答的指标

### 7.1 失败诊断

分别报告数学和代码：

- 首次失败数量；
- 截断数量；
- 格式错误数量；
- 局部计算或实现错误数量；
- 约束遗漏数量；
- 策略选择错误数量；
- 无法确定原因数量。

同时统计不同恢复动作的成功情况。

### 7.2 恢复率

至少报告：

- 初次失败、追加一次普通重试成功；
- 初次失败、定向修复成功；
- 初次失败、重新规划成功；
- 各方法仍然失败的任务数。

### 7.3 A 的贡献

比较 Failure-Aware Controller 与固定重试、确定性规则。

重点看：

- 救回了多少原本失败的题；
- 误触发了多少原本正确的题；
- 产生多少新的错误；
- 每恢复一道题需要多少额外 tokens；
- 是否优于同等预算的简单基线。

### 7.4 C 的额外贡献

在完全相同的任务和恢复预算下，比较：

`Controller + Memory`

与：

`Controller without Memory`

重点看：

- Memory 是否选择了不同恢复动作；
- 不同选择是否真实改变了结果；
- 是否存在来自不同任务的有效经验迁移；
- 是否比随机或打乱的 Memory 更好；
- 是否提高了成本效率。

不能把 A 带来的收益全部归因于 C。

### 7.5 正确率与 token

所有方法均需记录：

- 首轮正确率；
- 最终正确率；
- 输入 tokens；
- 输出 tokens；
- 总 tokens；
- 总 LLM 调用数；
- 平均每题成本；
- 每新增救回一题的成本；
- 测试阶段成本；
- 恢复经验构建成本。

同时展示正确率与 token 的权衡。

小样本无法提供严格统计结论，应报告配对差异和不确定性，不要把观察到的微小提升解释为机制已被证明有效。

## 八、继续研究的判断标准

本轮最终必须分别对方向 A 和 C 给出判断。

**方向 A：值得继续**

如果至少存在一些不能被简单固定重试稳定解决、但能够被可观察失败证据引导的定向干预恢复的题目，并且整体准确率—成本表现相较强简单基线出现积极信号，可以继续研究更好的失败检测与自适应预算。

**方向 C：值得继续**

如果冻结的 Recovery Memory 能在独立新题中改善恢复动作选择，并带来超过无经验控制器和打乱经验对照的真实收益，可以继续研究跨任务恢复经验学习。

**方向 C 不成立，但 A 成立**

应继续研究失败感知恢复，但暂时不再增加复杂的经验记忆机制。

**两者都不成立**

如果正确恢复主要来自普通重新采样，或者定向恢复的优势无法超过简单规则，则应明确建议停止当前设计，而不是继续堆叠 Controller、Memory 或 Prompt。

这些都是探索性 Go/No-Go 判断，不得把少量成功当作统计显著的性能保证。

## 十、最终回复必须直接给出的结论

请在完成实验后直接回答以下问题：

1. **DeepSeek Flash 失败的主要原因是什么？** 数学和代码是否存在明显差异？
2. **有多少失败题其实只需要重新采样？** 有多少确实需要改变恢复方法？
