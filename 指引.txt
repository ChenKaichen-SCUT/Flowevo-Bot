# Flowevo-Bot 下一阶段研究指引：Skill 质量、Admission 失败及成本机制的系统诊断

## 一、任务背景与目标

你现在是一名负责 LLM Agent 科研实验、算法分析与代码审计的高级研究工程师。

当前工作目录中已经有 Flowevo-Bot 项目。它融合了 FlowEvo 和 Buffer of Thoughts（BoT）的部分设计，目标是从历史数学解题轨迹中提炼可复用的中等粒度解题策略，并通过 Skill Admission 和 Cost-Aware Router，在保持正确率的同时减少后续 MATH 任务的 token 消耗。

此前已经完成一组真实实验：

| 指标 | FlowEvo（禁用 gold 反思） | Flowevo-Bot |
|---|---:|---:|
| 正确率 | 462/500（92.4%） | 464/500（92.8%） |
| 输入 tokens | 169,251 | 62,237 |
| 输出 tokens | 472,704 | 460,783 |
| 测试总 tokens | 641,955 | 523,020 |
| 包括建库的总 tokens | 1,437,390 | 1,592,751 |

相关实验采用相同的 500 道分层抽取 MATH 题、DeepSeek Flash，关闭了当前题 gold-answer reflection。

已有结论：

1. Flowevo-Bot 测试阶段减少了约 18.53% 的 token。
2. 两种方法正确率差异不显著。
3. 但 Flowevo-Bot 的建库成本较高，因此计入建库后总体成本反而上升。
4. **当前生成的 12 个候选 Skill 全部未成为 active。**
5. **Flowevo-Bot 的 500 道测试题全部走普通 LLM 解题路径。**
6. 因此，目前不能把测试阶段 token 减少归因于 BoT 策略复用。

本轮研究的核心任务是：

**系统诊断这 12 个 Skill 为什么没有被激活、它们是否具有真正的跨题泛化能力、当前 Admission/Router 是否存在过度保守或实现错误，以及后续应该如何改进。**

特别注意：

本轮以诊断和证据收集为主。不要为了让 Skill 被激活而直接降低阈值，更不要在未完成分析之前重写整个算法。

## 二、执行原则

### 2.1 优先使用已有数据

首先检查当前 Flowevo-Bot、FlowEvo 项目以及已有的实验日志、Skill Bank、checkpoint 和完整模型请求记录。

尽可能通过已有数据完成分析。

**默认禁止新增付费 LLM 调用。**

如果某项诊断必须重新调用 DeepSeek Flash，应说明：

- 为什么现有数据不足；
- 需要多少道任务；
- 预计多少次调用；
- 预计消耗多少 token；
- 该实验能够排除哪一种解释。

未经我明确同意，不得启动新的真实推理实验。

### 2.2 不修改原实验结果

本次不得：

- 覆盖已经完成的 500 题结果；
- 修改原 FlowEvo 源码；
- 修改历史 Skill Bank 快照；
- 更改历史正确率；
- 为提高 Skill 激活率而直接放宽 Admission；
- 使用测试集结果调参；
- 将模拟数据当作真实实验数据。

允许新增**只读诊断脚本**及必要的离线测试。

如果必须调整代码才能记录某种关键内部状态，应先保存原始版本，并明确标注此次修改属于 instrumentation，不属于算法改进。

### 2.3 禁止 Gold 泄漏

整个诊断过程中仍需区分：

- 训练题；
- 独立开发/验证题；
- 正式测试题。

测试题的 gold answer 只能供最终离线评分。

不能把当前测试题 gold 传给 solver、router、distiller 或 retry prompt。

尤其需要检查历史 Skill 是否源于经过 gold-feedback 修正的轨迹，不能仅依据最终答案正确就认定其来源合规。

- Admission 状态与原因。

如字段不存在，必须明确记录为 `missing`，不能推测。

## 3.2 生成人类可读的 Skill 清单

生成文件：

`reports/01_ALL_SKILLS.md`

每个 Skill 使用单独小节，完整展示它的真实策略内容。

我希望能直接阅读这份文档，判断：

> 它究竟是不是一个有适用条件、具有通用意义的解题套路？

例如，一个好的 Skill 可能是：

> 遇到某类素数整除条件时，先处理特殊素数，再通过同余约束缩小候选范围，最后回代验证。

而差的 Skill 可能只是：

> 遇到素数问题时，考虑使用数论方法。

这两种情况要明确区分。

## 3.3 评价 Skill 抽象质量

对 12 个 Skill 逐条进行诊断，重点检查：

1. **过于具体**：是否只适用于来源题目或简单换数字的变形？
2. **过于宽泛**：是否只是一般建议，无法实质缩短推理？
3. **粒度失衡**：是否太细以至于单次收益很小，或太大以至于几乎无法匹配？
4. **适用条件不清**：能否仅根据新题题面判断适用？
5. **数学正确性**：是否包含不成立的数学结论、遗漏条件或非法变形？
6. **重复性**：12 个 Skill 中是否存在实质相同的套路？
7. **组合潜力**：哪些可以合理组合，哪些组合可能互相干扰？
8. **成本潜力**：是否有能力替代一段真实推理，而不仅是增加一段 prompt？

对于每个 Skill，应给出：

- 诊断结论；
- 支撑该结论的原始证据；
- 当前尚未验证的疑点；
- 是否值得进入下一阶段独立验证。

没有充分数据时，应标记 `insufficient_evidence`，而不是主观认定有效或无效。

生成：

`reports/02_SKILL_QUALITY_REVIEW.md`

# 四、阶段二：逐条还原 Admission 为什么失败

当前 12 个 Skill 全部没有成为 active。

需要查明它们各自被哪一道门槛拦截。

## 4.1 审计 Admission 实现

找到并检查：

- Skill Admission 的入口；
- 全部验证规则；
- 全部阈值；
- 阈值来源；
- 各项判断的执行顺序；
- 当某个统计字段缺失时的处理逻辑；
- 是否存在默认拒绝行为；
- Skill 从 candidate/shadow 变成 active 的完整条件。

不能只报告最终 `active = false`。

必须尽可能恢复每个 Skill 的逐关判断过程。

## 4.2 建立 Admission 决策表

例如：

| Skill | 来源数量 | Dev 可用数 | 正确性 | 净节省 | 主要拒绝原因 |
|---|---:|---:|---|---|---|
| S01 | 实际值 | 实际值 | 实际值 | 实际值 | 实际原因 |
| S02 | 实际值 | 实际值 | 实际值 | 实际值 | 实际原因 |
| ... | ... | ... | ... | ... | ... |
| S12 | 实际值 | 实际值 | 实际值 | 实际值 | 实际原因 |

每个 Skill 不仅要记录**首次拒绝的门槛**，还应记录能够从已有数据判断出的其他未通过门槛。

特别区分以下情况：

**A. 质量失败**

Skill 本身存在数学错误、明显负迁移或适用条件不成立。

**B. 覆盖率不足**

Skill 可能正确，但独立验证题中很少出现适用结构。

**C. 样本不足**

并未发现明显错误，但有效验证数量过少，无法作出可靠判断。

**D. 成本不合算**

使用 Skill 后实际增加 token，或预期节省不足以抵消额外开销。

**E. 预测器缺乏数据**

Cost-Aware Router 没有足够的开发集统计，导致所有候选均被保守拒绝。

**F. 实现或配置问题**

例如字段没有正确传递、类别名称不匹配、状态转换错误、统计值缺失、阈值单位不一致等。

这些原因不能混为一谈，因为对应的算法改进完全不同。

生成：

`reports/03_ADMISSION_DIAGNOSIS.md`

`data/admission_decisions.jsonl`

其中 JSONL 应保留每个 Skill 的各门槛输入值、阈值、判断结果、缺失字段、首次拒绝点和所有可确定的失败原因。

# 五、阶段三：分析 Trigger、学科分类和未来复用机会

1. 学科类别一致的题数；

# 六、阶段四：专门审计 Cost-Aware Router

我非常关心这个模块是否过度保守。

因为现在所有 Skill 都没有被使用，可能出现：

> Skill 实际上有价值，但成本预测器无法证明它能节省 token，于是全部拒绝。

请检查：

1. Router 使用哪些特征？
2. 成本预测数据来自哪里？
3. 是否有足够的真实开发集样本？
4. 是否根据已观察的成本进行预测，还是用固定常数？
5. 当一个 Skill 完全没有使用历史时，如何估计它的收益？
6. 是否存在冷启动问题？
7. 哪些 Skill 是 Admission 拒绝，哪些是 Router 拒绝？
8. 如果没有任何 Skill 被实际使用，Router 是否永远无法积累真实收益数据？
9. Prompt 变短是否被错误地当作整个任务成本下降？
10. 是否正确计算了输入、输出和可能的 fallback 成本？

特别注意：

**Admission 和 Router 是两个不同阶段。**

如果 Skill 从未成为 active，那么测试中的 zero reuse 可能根本不是 Router 造成的。

必须先划清责任，不能笼统写“路由过于保守”。

# 九、阶段七：形成具体的算法改进建议

只有完成以上诊断，才能提出下一步修改方案。

不要一开始就决定“应该降低 Admission 门槛”。

根据真实证据，分别讨论：

### 方案 A：改进 Thought Distiller

适用于：

- Skill 太宽泛；
- Skill 太具体；
- 缺少明确 Trigger；
- 多道题没有被正确抽象；
- Skill 之间高度重复。

建议关注是否需要更好的多题聚类、策略抽象、技能合并和简短策略卡。

### 方案 B：改进 Skill Admission

适用于：

- Skill 有价值但独立验证数据不足；
- 阈值过于机械；
- 冷启动问题严重；
- 成本收益预测缺乏证据。

可以讨论 shadow evaluation、分阶段晋升、置信区间约束等机制。

### 方案 C：改进 Cost-Aware Router

适用于：

- Active Skill 已存在；
- 但 Router 经常错误拒绝；
- 成本预测严重偏差；
- 检索覆盖率不错但实际使用率很低。

### 方案 D：改变 Skill 的注入方式

适用于：

- Skill 复用有一定准确率帮助；
- 但输入 prompt 或输出推理增加；
- 整体无法节省 token。

可以研究更紧凑的宏策略、结构化提示、局部直接执行和动态缩短策略提示。

### 方案 E：调整 Skill 粒度或分类

适用于：

- 现有套路没有足够的未来复用机会；
- 过度细碎或过于宽泛；
- 学科标签无法有效代表解题结构。

可以研究学科内的策略家族、合理的宏策略粒度，以及有限的跨类别组合。

**每个改进建议必须引用本次诊断得到的具体证据，而不是泛泛提出更多复杂机制。**

最终给出优先级排序：

- 最值得先做的改进；
- 次优先级；
- 当前不建议做的改进。

每个建议还需包含：

- 预期解决的问题；
- 对应代码位置；
- 所需实验；
- 可能的失败原因；
- 是否会增加 API 成本；
- 该改进应由什么消融实验验证。
