# Flowevo-Bot 下一轮算法改进与正式实验执行指引

## 一、总体任务

你是一名负责 LLM Agent、数学推理、Skill Learning 和实验复现的高级研究工程师。

当前工作目录已有：

- FlowEvo 原始项目；
- Buffer of Thoughts（BoT）项目；
- 我们开发的 Flowevo-Bot 项目；
- 已完成的历史实验日志、12 个候选 Skill、Skill Bank 和 Admission 诊断报告。

本次任务必须在现有 Flowevo-Bot 基础上进行实际代码修改、测试和实验，不能只输出设计方案。

### 核心研究目标

我们希望结合 FlowEvo 和 BoT，从多道成功的数学解答中学习具有较高复用价值的**中等粒度数学解题宏策略（Reusable Reasoning Macro-Skills）**。

这些 Skill 应该：

1. 具有明确的数学适用条件。
2. 能够覆盖多道解题结构相似但不是简单替换数字的题目。
3. 可以按照 MATH 的学科类别组织和检索。
4. 不需要在新题中重新注入完整的历史解答。
5. 有机会减少模型重复推导所消耗的 tokens。
6. 使用后尽可能保持原始模型的正确率。
7. 如果不适用或成本不合算，可以选择完全不使用 Skill。

我们的目标不是提高 Skill 的数量或注入率，而是：

**在基本保持 MATH 解题正确率的前提下，通过真正有效的 Skill 复用降低总 token 成本。**

## 二、必须了解的已有实验与诊断结果

### 2.1 上一轮 500 题实验

使用相同的 500 道分层抽取 MATH 题，模型为 DeepSeek Flash。

已关闭 FlowEvo 的 gold-answer reflection 和重试。

| 指标 | FlowEvo | Flowevo-Bot |
|---|---:|---:|
| 正确题数 | 462 | 464 |
| 正确率 | 92.4% | 92.8% |
| 输入 tokens | 169,251 | 62,237 |
| 输出 tokens | 472,704 | 460,783 |
| 测试总 tokens | 641,955 | 523,020 |
| 含建库总 tokens | 1,437,390 | 1,592,751 |

关键结论：

- Flowevo-Bot 测试阶段节省 18.53% tokens。
- 其中绝大多数节省来自输入 token 减少。
- 两个系统的正确率差异不显著。
- Flowevo-Bot 的 12 个候选 Skill 全部未成为 active。
- 500 道 Bot 测试题全部走普通 LLM 解题路径。
- 因此测试阶段的节省不能归因于 BoT Skill。
- 计入建库成本后，Bot 总成本反而增加。

# 三、第一阶段：修复评测器与数据观测

这是后续实验的基础，必须先完成。

## 3.1 修复数学答案判分问题

此前诊断发现：

- 两次评分假阴性；
- 有格式差异被误判成数学错误；
- 有答案截断问题；
- 有些正负迁移信号并不是真实数学推导差异。

请检查当前数学答案提取和评分程序。

重点包括：

- LaTeX `\boxed{...}` 提取；

# 四、第二阶段：重新设计 Skill 的 Trigger 与数学 Guard

这是本次算法改进的第一重点。

## 4.1 当前存在的问题

原来的 Skill 使用简单关键词和特征集合匹配题目。

例如：

- `polynomial`
- `nonzero`
- `quadratic`
- `equation`
- `fraction`

然后要求多个前置条件同时出现。

这种方式无法准确表达数学套路的适用条件。

例如：

“满足 A 或 B”被实现成“必须同时满足 A 和 B”。

又如，有理式方程需要检查分母不为零，但题目未必显式出现 `nonzero` 一词。

因此，新的 Skill 系统必须区分：

**Trigger：什么时候值得考虑这个套路？**

**Guard：执行套路中的某一步时，必须满足哪些数学条件？**

不能把二者混在一起。

## 4.2 新的 Trigger 结构

建议使用结构化逻辑表达式，至少支持：

- `all_of`
- `any_of`
- `not`
- `optional`
- `guard`

例如：

`any_of` 中可以包含“有理式方程”或“有理式不等式”两种结构。

在求解阶段再检查：

- 分母是否非零；
- 变形是否等价；
- 不等式乘除时符号是否明确；
- 是否引入增根；
- 是否存在遗漏的定义域约束。

实现这些逻辑时，需要明确的 schema、验证器与可测试的解释结果。

不要直接把自然语言前置条件解释成简单字符串集合包含关系。

## 4.3 改进数学特征提取

在 `features.py` 等相关模块中，将词面匹配和数学结构识别分开。

优先考虑：

- 学科类别；
- 数学表达式形态；
- 方程/不等式结构；
- 有理式；
- 多项式阶数；
- 可识别的对称表达式；
- 因式分解结构；
- 模运算与整除约束；
- 数列与递推关系；
- 三角表达式；
- 计数问题中的顺序、重复和约束结构。

不要因为字符串里出现 `^2` 就判定是二次结构，也不能因为题面没有写 `nonzero` 就认为分母非零条件无法处理。

无法可靠解析的结构应当标记为不确定，并保留安全回退路径。

默认避免为了特征提取新增 LLM 调用。

## 4.4 Skill 来源自匹配

增加一个新的低成本检查。

每个候选 Skill 生成后，先用它的 Trigger 对来源题重新匹配。

记录：

- 来源题总数；
- Skill 声称应当适用的来源题数；
- 真正匹配数；
- 匹配失败原因。

如果一个 Skill 声称适用于所有来源题，但实际一个都匹配不上，应当退回候选修订阶段。

如果某些来源题本来就不满足抽象出的具体策略，不应强制要求全部匹配，而应检查这些题是否应该被移出该策略聚类。

**来源自匹配只是必要的内部一致性检查，不能证明 Skill 具有跨题泛化能力。**

## 4.5 输出

- `reports/02_TRIGGER_GUARD_REDESIGN.md`
- `data/source_self_match.csv`
- 修复后的 Skill Schema
- 特征提取测试
- OR/AND 逻辑测试
- 数学 Guard 测试

# 五、第三阶段：改进 BoT Thought Distiller

目标是自动生成真正的解题套路，而不是关键词相似的历史解答摘要。

## 5.1 改进聚类方式

目前系统使用题目特征、策略标签与解答关键词进行聚类。

本次改进应当更关注**解题过程中真实发生的数学变换**。

例如：

- 有理式代换后降阶；
- 对称表达式化简；
- 分组因式分解；
- 同余约束筛选；
- 先分类再计数；
- 几何关系代数化；
- 三角恒等式变换。

不能仅因为两道题都出现 `reduce` 或 `factor` 就认定它们采用同一种方法。

也不能仅因文字不同就拆开数学结构相同的题。

## 5.2 Skill 粒度

不要提炼成过细的操作：

- 加法；
- 乘法；
- 简单求模；
- 一次代换。

也不要提炼成过于笼统的建议：

- 仔细分析题目；
- 使用代数方法；
- 考虑分类讨论；
- 检查结果。

应当提炼中等粒度的数学宏策略。

例如：

**有理式降阶与定义域恢复**

当方程具有某种可消元的有理表达式结构时，先检查定义域，再通过代换或等价变形降低问题复杂度，解出简化后的问题，最后回代并排除不满足原式的解。

这样的 Skill 应当能覆盖多个具有相似解题结构、但不是简单替换数值的题目。

## 5.3 多题学习

默认不从单个成功解答直接激活 Skill。

优先聚合多道正确题，寻找共同策略。

如果一个候选套路只能从一道题中观察到，应先保持候选状态，等待更多独立证据。

不能为了达到来源数量阈值，强行将不同解题套路聚在一起。

## 5.4 短 Prompt

每个 Skill 应保存：

- 完整版本；
- 短策略版本；
- Trigger；
- Guard；
- 来源；
- 验证统计；
- 历史 token 效果。

正式注入时优先使用短策略版本。

初期可以把短 Prompt 预算设为 100 tokens 左右，并允许进行长度消融。

压缩时不能丢失影响数学正确性的必要条件。

## 5.5 优先处理 S07、S04

**S07：有理式降阶**

重点修复：

- 题目结构识别；
- 有理式相关 Trigger；
- 分母非零 Guard；
- 合法变换与回代检查；
- 原来源题的正确匹配。

**S04：分类计数**

重点修复：

- 是否考虑排列顺序；
- 是否允许重复；
- 是否需要互斥分类；
- 对称情形下除以重复计数因子的合法性；
- 禁例与重复计数处理。

其他候选 Skill 也要重新检查，但不要假设所有 12 个都应该保留。

## 5.6 输出

- `reports/03_DISTILLER_IMPROVEMENTS.md`
- `data/skills_v2_full.json`
- `data/skill_old_new_comparison.csv`
- 新 Skill 来源与聚类记录
- 新旧 Skill 数量、长度与重复程度统计

保留原有 Skill Bank，不要覆盖。

# 六、第四阶段：完善 Admission，但不要直接放宽门槛

这一阶段需要解决 Skill 冷启动问题。

## 6.1 分离 Admission 和 Router

Skill Admission 决定：

> 这条 Skill 是否已经具备足够证据进入活跃库？

Cost-Aware Router 决定：

> 对于某道具体新题，是否值得使用某个已激活 Skill？

两者必须分离。

不能让一个从未参与解题的 Skill，因为缺乏历史复用统计而永久没有获得验证机会。

## 6.2 引入 Shadow Validation

新 Skill 默认进入 `candidate`。

通过来源自匹配、数学条件检查后进入 `shadow`。

在独立开发题中进行受控验证，比较：

- 不注入 Skill；
- 注入旧 Skill；
- 注入修复后的新 Skill。

Shadow 实验只能使用 train/dev 数据，不能根据正式测试题表现决定 Skill 入库。

## 6.3 Admission 判断

除了来源数量和匹配情况，还应重点考察：

- 独立验证覆盖率；
- 数学条件是否正确；
- 是否观察到负迁移；
- 输入 token 增量；
- 输出 token 变化；
- 总 token 净收益；
- 是否存在明显的跨题泛化。

当数据不足时，应继续保持 shadow，而不是自动拒绝所有 Skill，也不能直接假设 Skill 有效。

## 6.4 检查 Router 冷启动

上一轮诊断指出，当前 Router 的 confidence 与严格风险门槛可能需要较多验证样本。

请分析：

- 实际需要多少独立样本；
- 是否与当前开发集规模冲突；
- 是否存在所有 Skill 永远无法进入 active 的闭环；
- 是否能够通过开发集的 Shadow Validation 积累必要证据。

不要为了激活 Skill 就直接降低正确率约束。

需要在报告中区分：

- Skill 因数学条件不可靠被拒绝；
- Skill 因观察到真实负迁移被拒绝；
- Skill 因验证数据不足而尚未被批准。

## 6.5 输出

- `reports/04_ADMISSION_V2.md`
- `data/admission_v2_decisions.jsonl`
- `data/shadow_validation_summary.csv`
- 新的 Admission 离线测试

# 七、第五阶段：小规模真实实验

在大规模 500 题测试前，先确认是否有真正具备复用价值的 Skill。

## 7.1 数据来源

优先使用现有正确轨迹和独立开发题。

不要重新生成已经存在且满足来源要求的训练轨迹。

对 S07、S04 优先寻找符合其真实数学结构的独立验证题。

建议第一轮选约 20 道适合目标策略的独立开发题。

如果现有开发数据不足，可从尚未使用的训练/开发候选中补充，但不得从最终测试题中挑选样本来优化 Skill。

## 7.2 比较组

至少包括：

**A：Bot-NoBank**

不加载任何 Skill，不进行 Skill 注入，直接调用原始 DeepSeek Flash 数学求解。

**B：Bot + Original Skill**

使用修复之前的原始策略内容，作为机制对照。

**C：Bot + Revised Skill**

使用本轮重新设计的结构化策略。

三组使用相同的模型、题目和可比较的生成配置。

对于无法可靠匹配 Skill 的任务，不能强行注入。

## 7.3 主要指标

逐题记录：

- 题目 ID；
- 学科；
- 原始类别；
- 使用的 Skill；
- Trigger 是否匹配；
- Guard 是否通过；
- 模型最终答案；
- 正确性；
- 输入 tokens；
- 输出 tokens；
- 总 tokens；
- 是否截断；
- 是否遇到解析错误。

特别要记录：

**没有 Skill 时正确、用了 Skill 后错误的题。**

以及：

**没有 Skill 时错误、用了 Skill 后正确的题。**

不能仅根据总体正确率判断策略是否有用。

## 7.4 进入正式实验的条件

只有在独立开发数据上出现可解释的积极证据，且至少有一条经过验证的 Skill 能实际进入活跃库，才运行完整 500 题实验。

进一步检查：

- Skill 是否存在真实的跨题覆盖；
- 是否观察到总 token 节省；
- 是否有明确数学错误或明显负迁移；
- 结果是否只是偶然的输出长度变化。

如果改进后的 Skill 仍然完全无法获得活跃资格，应停止正式 500 题测试，先输出失败分析，不要为了完成任务而强行运行无意义的大规模实验。

小规模验证完成后保存全部数据和 Skill Bank 快照，不得使用正式测试结果重新筛选策略。

# 八、第六阶段：正式 MATH 500 题实验

这是本轮最重要的性能验证。

若第五阶段达到继续条件，则启动正式实验。

## 8.1 模型与并发设置

必须沿用之前的主要实验配置：

**模型：DeepSeek Flash**

**API 最大并发：64**

**本地计算最大并行：12**

注意：

- 64 是同一实验调度器的全局 API 并发上限，不是每个实验组各开 64。
- 本地 CPU 并行上限为 12。
- 并发主要提高运行速度，不应改变算法的数学判断。
- 对 HTTP 429、超时和其他基础设施错误，可采用有界重试及退避。
- 基础设施重试必须与模型求解失败、反思重试严格区分。
- 不允许因为数学答案错误而自动获得额外 API 调用。
- 使用与既有实验可比较的 temperature、最大生成 token 及输出格式。
- 记录实际模型标识、endpoint 与请求设置。

## 8.2 测试数据

使用之前同一批分层抽取的 MATH 500 道题，保持：

- 完全相同的 task ID；
- 完全相同的题目内容；
- 完全相同的学科构成；
- 完全相同的评估规则。

保存任务 manifest 和 hash。

注意：这一批题目已经用于历史实验与研究决策，因此应将其标记为**既有基准上的确认/回归实验**，不能宣称它是全新的、从未用于模型开发的严格 holdout。

如需在论文中提出最终泛化结论，应另行准备从未用于阈值选择与算法调试的冻结测试集。

不能根据这 500 题的结果继续修改 Skill 后再把同一批成绩当成独立验证。

## 8.3 正式比较方法

建议至少比较以下三个方法。

### A. Bot-NoBank

使用 Flowevo-Bot 已有的无 Skill 推理路径。

这是真正重要的成本基线。

因为上轮实验的 Bot 500 题没有使用任何 Skill，却已经比 FlowEvo 节省了 18.53% tokens。

### B. FlowEvo-GoldFree

原版 FlowEvo，关闭 gold-answer reflection 和数学正确性驱动的原生重试。

保留其原有历史上下文机制作为研究对照。

### C. Flowevo-Bot-V2

使用本轮修订并经过开发集验证的 Skill Bank。

开启：

- 学科分类；
- 结构化 Trigger；
- 求解期 Guard；
- Skill Admission；
- Cost-Aware Router；

## 8.4 实验公平性

**Bot-NoBank 与 Bot-V2 的主要差异应当只是 Skill 机制。**

必须保证：

- 相同 DeepSeek Flash；
- 相同题目；
- 相同基础 system/user prompt；
- 相同输出格式；
- 相同解题调用预算；
- 相同截断设置；

FlowEvo 原始方法可以保留其原生 prompt，作为系统级比较，但要列出这些差异，不能把它当作严格单因素对照。

## 8.5 保持 Gold-Blind
